# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

The Quartz static site that publishes https://wiki.theloop.community. Its
`gh-pages` branch is what GitHub Pages actually serves; `main` holds the
site config, theme, and plugin sources.

This repo (`djsprenk/theloopwiki`) and the separate
`theloopwiki-tools` repo are **two separate git repos with two separate
GitHub remotes** — see the parent `theloopwiki-tools/CLAUDE.md` for the
full rationale. Content is filtered and pushed into `../content` by that
repo's `publish.sh` / `filter.py`; this repo never touches the vault
directly.

## Commands

Local dev/preview (serves whatever is in `../content`, no deploy):

```
npx quartz build --serve --directory ../content
```

Quartz's own test/lint commands:

```
npm run check   # tsc --noEmit && prettier --check
npm test        # tsx --test
```

## Locally-forked plugins

`.quartz/plugins/` is gitignored and managed by Quartz's plugin CLI
(`npx quartz plugin add/install/update`) — anything edited there directly
is lost the next time plugins are reinstalled or synced from
`quartz.config.yaml`/`quartz.lock.json`.

When a plugin's exposed config options aren't enough (e.g. changing literal
text/markup, not just data), fork it into `local-plugins/<name>/` instead,
which **is** tracked in git. Register it with:

```
npx quartz plugin add ./local-plugins/<name>
```

This symlinks `local-plugins/<name>` into `.quartz/plugins/<name>` and
updates `source:` in `quartz.config.yaml` to the local path — the fork
survives future `.quartz/` regeneration.

**Gotcha:** after editing a local fork's `src/`, `npx quartz plugin update
<name>` (or `install --latest`) does NOT recompile it — it reports "using
pre-built dist/" and silently keeps serving the stale build. Rebuild
manually:

```
cd local-plugins/<name>
npx tsup
```

Then re-run `npx quartz build` to pick up the new `dist/`.

Current forks:

- `search` (`local-plugins/search/`) — the upstream
  `github:quartz-community/search` plugin hardcodes the search overlay's
  backdrop blur (`backdrop-filter: blur(4px)` in
  `src/components/styles/search.scss`) with no config option for it.
  Forked solely to bump that literal to `blur(30px)` for a stronger
  frosted-glass effect behind the search modal — no other behavior changed.
- `footer` (`local-plugins/footer/`) — the upstream
  `github:quartz-community/footer` plugin only exposes a `links` option,
  not the footer message text. Forked to render "The Loop © {year} -
  Created with Quartz v{version}", with "The Loop" linking to
  https://theloop.community. The `GitHub`/`Discord Community` links list
  was removed by setting `options.links: {}` on this plugin's entry in
  `quartz.config.yaml`, rather than in the fork itself.
- `folder-page` (`local-plugins/folder-page/`) — the upstream
  `github:quartz-community/folder-page` plugin's `FolderContent` component
  always appends the auto-generated by-date file listing below any content
  in a folder's index note, with no option to suppress it. Forked to add
  `hideListingWhenIndexed` (default `true`): when the folder's index page
  has real authored content — either a literal `index.md`, or the Obsidian
  "folder note" convention (a file named identically to its parent folder,
  e.g. `The Loop Academy/The Loop Academy.md`) — the listing is skipped
  entirely and only the authored content shows. Folders with no authored
  index still get the normal listing (this is how "has real content" is
  detected: the rendered HAST tree is non-empty vs. empty for
  auto-generated virtual folder pages).
- `explorer` (`local-plugins/explorer/`) — the upstream
  `github:quartz-community/explorer` plugin's `filterFn` option can only be
  set via a TypeScript override (`quartz.ts`), not from
  `quartz.config.yaml`, which this repo doesn't use. Forked to extend the
  plugin's own default `filterFn` (which already excludes the `tags`
  folder) to also exclude the top-level `Meta` folder — internal authoring
  scaffolding (e.g. `.base` files backing embedded database views, see
  `filter.py`'s `EXCLUDED_FOLDERS` in the sibling `theloopwiki-tools` repo)
  that still needs to be built as a real page (so embeds of it render) but
  shouldn't appear in site navigation, search, or the graph. Matches only a
  folder named exactly `meta` at the vault root (`node.slugSegments.length
=== 1`) — nested folders elsewhere named `Meta` are unaffected. Also
  extends the default `sortFn` to sort by a note's `order` frontmatter (the
  same numeric field vault notes already use to sort rows in embedded Base
  views, populated into `contentIndex.json` by the `content-index` fork
  below): within each existing folders-vs-files group, items with an
  explicit `order` sort first by that value ascending, and any remaining
  items fall back to the prior alphanumeric-on-`displayName` behavior. A
  folder's own `order` comes from its index page's frontmatter (same
  `data` object used for `hideListingWhenIndexed` detection in
  `folder-page`) — a folder with no authored index note has no `order` and
  sorts into the alphabetical tail, same as before this change. Edited in
  both `src/components/Explorer.tsx` (server-side default, gets
  `.toString()`-serialized into each page's inline data) and
  `src/components/scripts/explorer.inline.ts` (client-side fallback used
  only if that serialized data fails to parse) — keep the two in sync.
- `content-index` (`local-plugins/content-index/`) — the upstream
  `github:quartz-community/content-index` plugin's `ContentDetails` type
  (what becomes each entry in `static/contentIndex.json`, which
  `explorer`, search, graph, backlinks, etc. all read) has no `order`
  field, so a note's `order` frontmatter was invisible outside of Base
  views. Forked to add `order?: number` to `ContentDetails` and populate it
  from `frontmatter.order` in `emitAll` (left `undefined`, not `0`, when
  absent or non-numeric) — no other behavior changed. This is what makes
  the `explorer` fork's `order`-aware `sortFn` (above) possible.

Custom (non-fork) local plugins:

- `related-links` (`local-plugins/related-links/`) — no upstream equivalent;
  scaffolded from the `description`/`bases-page` plugin templates. A
  markdown-stage transformer, registered at `order: 20` (between
  `note-properties` at 5, which populates `file.data.frontmatter`, and
  `obsidian-flavored-markdown` at 30, which converts `wikilink`-type mdast
  nodes into real links). Reads a note's `related` frontmatter (a list of
  `[[Target|Alias]]` wikilinks) and appends a `## See Also` heading plus an
  Oxford-comma-joined paragraph of links to the end of the content tree —
  omitted entirely when `related` is empty or absent. Also reads a `next`
  frontmatter field (a single `[[Target|Alias]]` wikilink, not a list) and,
  if present, appends a `## Next Up` heading plus a single-link paragraph
  _after_ the `See Also` block — this is what replaces a hand-typed "Next
  lesson: [[...]]" line at the bottom of course pages. Both sections
  construct `wikilink`-type mdast nodes directly (the same shape
  `@quartz-community/remark-obsidian` produces for body wikilinks) rather
  than resolving hrefs itself, so OFM and `crawl-links` (order 60) resolve
  and style them identically to hand-written body links, including the same
  non-blocking behavior for a dead/ambiguous target (renders as a link that
  may 404, doesn't fail the build) — `filter.py`'s
  `extract_frontmatter_link_targets` in the sibling `theloopwiki-tools` repo
  separately flags those (for both `related` and `next`) during publish.

## Folder click → specific page (not the auto listing)

Two related but distinct customizations exist for folder index pages:

- **Suppress the listing, keep your own content**: write real content in
  the folder's index note (`index.md`, or the folder-note-with-matching-name
  convention above). The `folder-page` fork's `hideListingWhenIndexed`
  handles the rest automatically — no extra frontmatter needed.
- **Redirect straight to a different page entirely** (skip even your own
  index content): add `aliases:` to the _target_ page's frontmatter, with
  the full absolute slug of the folder's index page, e.g.:

  ```yaml
  aliases:
    - the-loop-academy/01-foundations-of-djing/index
  ```

  Must be the **full absolute slug**, not a relative path — `alias-redirects`'s
  relative-URL resolver explicitly refuses anything ending in `index`, so a
  bare `index` alias resolves to the site root instead of the folder. This
  works reliably (not a race) because Quartz's build (`quartz/build.ts`)
  always runs `PageTypeDispatcher` — which renders the folder's own
  listing/content page — in Phase 1, then all other emitters, including
  `AliasRedirects`, in Phase 2. Phase 2's redirect HTML always overwrites
  the Phase 1 output at that path.

## Encrypted (password-protected) content

Course content is published with per-page passwords via the
`encrypted-pages` community plugin (AES-256-GCM, decrypted client-side).
Every note under `The Loop Academy/` currently has a `password:` frontmatter
field, which means:

- Built HTML for those pages has no visible content in the raw output —
  the entire HAST tree is replaced with an opaque ciphertext container at
  build time. `grep`-ing built HTML/CSS for page content will find nothing;
  verifying visual/content changes requires an actual browser with the
  password entered.
- `static/encryptedContentIndex.json` is a companion "shadow" content index
  for `unlisted: true` encrypted pages, regenerated on every build.
- `encrypted-pages` (`local-plugins/encrypted-pages/`) is itself forked
  (not just configured) so its shadow-index entries carry `order?: number`,
  populated from `frontmatter.order` in `buildShadowEntry`
  (`src/emitter.ts`) the same way the `content-index` fork does for
  unencrypted pages. Without this, an encrypted page's sidebar position was
  always alphabetical: `unlisted: true` pages are excluded from
  `contentIndex.json` entirely, so the client-side `explorer` fork's
  `order`-aware `sortFn` had nothing to sort by until the shadow index
  patches the decrypted entry back in at runtime
  (`encrypted.inline.ts`'s `applyShadowPatches`, which fires a `render`
  event `explorer` re-sorts on) — and that patch previously carried no
  `order`, so newly-unlocked pages would sort to the alphabetical tail and
  visibly reflow relative to any already-ordered siblings.

See `docs/plugins/EncryptedPages.md` for the full plugin behavior
(`unlisted` vs `stealth` pages, shadow index format, config options).
